# Implementation

프로젝트의 주요 설계 및 구현 내용을 정리했습니다.

## JWT 기반 인증 및 사용자 식별 구조

초기에는 사용자, 판매자, 관리자의 식별값으로 `userId`, `sellerId`, `adminId`를 직접 사용하는 구조를 고려했지만, 로그인 ID가 서비스 내부 식별자로 계속 사용되는 것은 보안 및 데이터 관리 측면에서 적절하지 않다고 판단했습니다.

그래서 사용자, 판매자, 관리자는 각각 내부 기본키인 `userNo`, `sellerNo`, `adminNo`를 기준으로 식별하도록 변경했습니다.

- 사용자: `userNo`
- 판매자: `sellerNo`
- 관리자: `adminNo`

로그인 ID는 인증 및 계정 확인에 필요한 경우에만 별도 API로 조회하도록 분리하고, 일반적인 API 처리에서는 내부 기본키를 기준으로 동작하도록 구성했습니다.

이를 통해 로그인 ID 노출을 줄이고, 프론트엔드와 백엔드 간 API 흐름에서도 내부 식별자 중심으로 일관되게 처리할 수 있도록 했습니다.

## BFF 연동을 고려한 인증 역할 분리

본 프로젝트는 Next.js API Route를 BFF 계층으로 사용합니다.

로그인, Access Token 생성, Refresh Token 재발급과 같은 클라이언트에 가까운 인증 흐름은 Next.js API Route에서 처리하고, Spring Boot API는 전달받은 토큰의 유효성을 확인한 뒤 DB의 Refresh Token 저장/교체와 서비스 데이터 처리를 담당하도록 역할을 분리했습니다.

- Next.js API Route: 토큰 생성, 쿠키 설정, 토큰 재발급, 프론트 요청 중계
- Spring Boot API: 토큰 유효성 검사, Refresh Token DB 저장/교체, 실제 도메인 데이터 처리

휴대폰 인증, 비밀번호 변경 등 일회성 인증 흐름도 토큰 목적에 따라 분리했습니다.

- 휴대폰 인증 Token
- 휴대폰 인증 완료 Token
- 비밀번호 변경 Token

비밀번호 변경처럼 보안적으로 중요한 흐름은 Spring에서도 토큰 유효성을 다시 확인하도록 했고, 회원가입/회원정보 수정처럼 Next.js API 계층에서 검증 가능한 흐름은 BFF에서 검증 후 Spring API를 호출하는 방식으로 역할을 나눴습니다.

## Interceptor 기반 인증 처리

Spring MVC `HandlerInterceptor`를 사용하여 API 요청의 `Authorization` Header를 검사했습니다.

요청에 Bearer Token이 포함되어 있으면 JWT를 파싱하고, token type에 따라 내부 기본키를 request attribute에 저장했습니다.

- `ACCESS` → `userNo`
- `SELLER` → `sellerNo`
- `ADMIN` → `adminNo`

컨트롤러에서는 아래와 같이 필요한 인증 정보를 주입받아 사용합니다.

```java
@RequestAttribute(value = "userNo", required = false) Integer userNo
```

## 공통 예외 처리 구조

비즈니스 예외를 `BusinessException`으로 정의하고, `ErrorCode` enum을 통해 HTTP 상태 코드, 에러 코드, 기본 메시지를 관리했습니다.

`GlobalExceptionHandler`에서 예외를 공통 응답 형식으로 변환하여 프론트엔드와 Next.js API Route에서 `message`, `detail` 기준으로 일관되게 처리할 수 있도록 구성했습니다.

이를 통해 인증 오류, 유효성 오류, DB 오류, 구매/쿠폰/재고 관련 오류를 공통된 방식으로 응답할 수 있도록 했습니다.

## 상품 목록 Cursor Pagination

상품 목록 조회는 cursor 기반 pagination으로 구현했습니다.

페이지 크기보다 1개 더 조회하여 다음 페이지 존재 여부를 판단하고, 정렬 조건에 따라 다음 요청에 사용할 cursor 값을 생성했습니다.

- `POPULAR`: 조회수 + 위시 수 기준
- `LATEST`: 생성일 기준
- `PRICE_LOW`, `PRICE_HIGH`: 가격 기준

또한 상품 목록에 필요한 이미지는 productId 목록 기준으로 한 번에 조회한 뒤, productId별로 그룹핑하여 응답 데이터에 주입했습니다.

이를 통해 상품 목록 조회 시 반복적인 이미지 조회를 줄이고, 프론트엔드의 무한 스크롤 구조와 연결할 수 있도록 구성했습니다.

## 장바구니 재고 반영 처리

장바구니 추가 시 기존에 담긴 상품 옵션은 수량을 증가시키고, 없는 옵션은 새로 추가하도록 분리했습니다.

요청 수량이 재고를 초과하는 경우 실제 반영된 수량을 기준으로 응답을 구분했습니다.

- 전체 반영 성공
- 일부 수량만 반영
- 재고 부족으로 반영 실패

이를 통해 프론트엔드에서 `CART_ADD_SUCCESS`, `CART_ADD_PARTIAL_SUCCESS`, `CART_ADD_OUT_OF_STOCK` 상태에 따라 사용자에게 다른 안내를 제공할 수 있도록 구성했습니다.

## 구매 페이지 재고 선점 구조

바로구매와 장바구니 구매 시 `stock_hold` 기반으로 구매 진행 중인 수량을 임시 선점하도록 설계했습니다.

- 구매 페이지 진입 시 기존 활성 hold를 정리하고 새 요청 기준으로 재고 선점
- 같은 상품 옵션 요청은 수량을 병합하여 처리
- 가용 재고를 확인한 뒤 hold upsert 수행
- 최종 hold 수량이 요청 수량과 일치하는지 검증
- hold 상태와 만료 시간을 기준으로 유효 선점 수량 계산
- 결제 완료 시 주문 생성, 재고 차감, hold 상태 변경

이를 통해 결제 전 단계에서 여러 사용자가 같은 재고를 동시에 구매하는 상황을 줄일 수 있도록 구성했습니다.

## 쿠폰 적용 구조

쿠폰 마스터, 사용자 보유 쿠폰, 상품 제한 쿠폰 정보를 분리하여 관리했습니다.

구매 페이지 진입 시 선택된 쿠폰은 사용자 쿠폰으로 다운로드한 뒤, `stock_hold`와 연결되는 `stock_hold_coupon` 형태로 저장하여 결제 단계에서 다시 검증할 수 있도록 구성했습니다.

- 전체 상품 적용 쿠폰
- 특정 상품 제한 쿠폰
- 중복 가능 / 불가능 쿠폰
- 정률 / 정액 할인
- 최대 할인 금액
- 최소 주문 금액
- hold 기준 쿠폰 매핑
- 결제 시 쿠폰 사용 가능 여부 재검증

이를 통해 구매 페이지에서 선택한 쿠폰 정보가 결제 시점까지 유지되면서도, 실제 결제 전 다시 검증될 수 있도록 구성했습니다.

## 주문/결제 트랜잭션 처리

결제 요청은 `@Transactional`로 처리하여 주문 생성, 재고 차감, 쿠폰 사용, 마일리지 변경, hold 상태 변경이 하나의 흐름으로 처리되도록 구성했습니다.

- 요청 holdId 정합성 검증
- 적용 쿠폰 사용 가능 여부 검증
- 배송비, 쿠폰 할인, 마일리지, 적립금 계산
- 주문 그룹 및 주문 아이템 생성
- 상품 옵션 재고 차감 및 판매 수량 증가
- 쿠폰 사용 처리
- 마일리지 차감/적립 처리
- `stock_hold` 상태를 결제 완료 상태로 변경
- 장바구니 구매 건은 결제 완료 후 장바구니 삭제

이를 통해 결제 과정 중 일부 단계에서 오류가 발생할 경우 DB 변경 작업이 일관되게 롤백될 수 있도록 구성했습니다.

## 파일 업로드 및 정적 리소스 제공

상품 이미지 파일은 서버 업로드 경로에 저장하고, 저장된 파일은 `/uploads/**` 경로로 접근할 수 있도록 정적 리소스 매핑을 구성했습니다.

이미지 업로드 시에는 파일 확장자, 파일 크기, MIME 타입을 검증하고 UUID 기반 저장 파일명을 생성하여 원본 파일명과 저장 파일명을 분리했습니다.

- jpg, jpeg, png, gif, webp 확장자 허용
- 파일 크기 제한
- `image/*` MIME 타입 검증
- UUID 기반 저장 파일명 생성
- 업로드 경로 기반 정적 리소스 제공
