# Troubleshooting

프로젝트를 진행하며 발생한 주요 문제와 해결 과정을 정리했습니다.

## 1. 로그인 ID 기반 식별 구조 개선

### 문제

초기에는 사용자, 판매자, 관리자의 식별값으로 `userId`, `sellerId`, `adminId`를 API 흐름에서 사용하는 구조였습니다.

하지만 로그인 ID가 여러 API 응답과 내부 처리 과정에서 계속 사용되면 계정 식별 정보가 불필요하게 노출될 수 있고, DB 관계 설정에서도 변경 가능성이 낮은 내부 기본키를 사용하는 편이 더 적절하다고 판단했습니다.

### 원인

로그인 ID와 내부 식별자의 역할이 분리되어 있지 않아 인증, 조회, 수정 API에서 로그인 ID가 서비스 내부 식별자처럼 사용되고 있었습니다.

### 해결

- 사용자, 판매자, 관리자의 내부 식별자를 `userNo`, `sellerNo`, `adminNo`로 변경
- JWT payload와 request attribute에서도 내부 기본키를 사용
- 일반 회원정보 조회 응답에서는 로그인 ID를 제외
- 로그인 ID가 필요한 경우에만 별도 API로 조회하도록 분리

### 결과

로그인 ID 노출을 줄이고, API 처리와 DB 관계를 내부 기본키 중심으로 일관되게 정리할 수 있었습니다.

## 2. 구매 진행 중 재고 초과 주문 가능성 개선

### 문제

결제 완료 시점에만 재고를 차감하면, 여러 사용자가 동시에 같은 상품을 구매 페이지까지 진행하는 상황에서 재고 초과 주문이 발생할 가능성이 있었습니다.

### 원인

구매 페이지 진입 후 결제 전까지의 수량이 재고 계산에 반영되지 않으면, 실제로는 다른 사용자가 구매를 진행 중인 수량도 여전히 구매 가능한 재고처럼 보일 수 있었습니다.

### 해결

- 구매 페이지 진입 전 `stock_hold` 생성
- 재고 조회 SQL에서 활성 hold 수량 제외
- 같은 상품 옵션 요청은 수량을 병합하여 처리
- holdId 기준으로 구매 페이지 상품/쿠폰 상태 관리
- 구매 페이지 조회 및 주기적 API 호출로 hold 연장
- 결제 완료 시 hold 상태를 결제 완료 상태로 변경
- 오류/만료 시 returnUrl 기준으로 복귀 흐름 처리

### 결과

결제 전 단계의 구매 진행 수량도 재고 계산에 반영하여, 재고 초과 주문 가능성을 줄일 수 있었습니다.

## 3. 프론트엔드와 백엔드의 에러 처리 방식 통일

### 문제

API마다 다른 방식으로 오류를 반환하면 Next.js API Route와 프론트엔드에서 에러 처리가 분산되고, 화면별로 예외 처리가 달라질 수 있었습니다.

### 원인

인증 오류, 유효성 오류, DB 오류, 구매/쿠폰/재고 오류가 각각 다른 응답 형태로 내려오면 프론트엔드에서 공통 처리하기 어렵습니다.

### 해결

- `BusinessException`으로 비즈니스 예외 정의
- `ErrorCode` enum에서 HTTP 상태 코드, 에러 코드, 기본 메시지 관리
- `GlobalExceptionHandler`에서 공통 응답 형태로 변환
- Next.js API Route와 React Query에서 동일한 에러 응답 구조를 기준으로 처리

### 결과

프론트엔드에서 API 오류를 `message`, `detail` 기준으로 일관되게 처리할 수 있게 되었고, 인증/구매/쿠폰 관련 예외 대응 흐름을 단순화할 수 있었습니다.
